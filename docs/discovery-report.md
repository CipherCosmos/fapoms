## 1. Executive Understanding ✅

**FAPOMS** (internal engineering name; the product is branded **"Sumeru Audit Suite"** in the web app and **"Karat"** on mobile, publisher "Sumeru Global") is a **field-audit operations platform**. Banks and NBFCs (the platform's *clients*) contract Sumeru Global to physically visit and audit their own branches — verifying what's actually at a location, collecting paperwork, and producing a signed record of the visit. FAPOMS is the system that runs that business end to end: it holds the contract/branch list, decides who should visit which branch and when, negotiates and dispatches the visit to a field appraiser ("**assayer**"), receives back what the assayer captured, routes it through a back-office data-entry/validation desk, and turns a completed visit into a bill (both what the client owes and what the assayer is owed). `VERIFIED — RUNTIME` (login screen copy: *"Plan the work, send the right assayer, capture what they find, and keep the evidence together — from the branch visit to the signed report."*) + `VERIFIED — CODE` (module map).

The business problem it solves: coordinating a **distributed, non-employee field workforce** (hundreds of independent assayers, not on payroll) against a constantly changing list of client branches, while keeping an auditable chain of custody on the paperwork each visit produces and reconciling money in both directions (client billing, assayer payout) against a single source of truth. `INFERRED` from the entity/workflow model — to be corroborated by client-side and billing-role journeys in a later session.

**Finding — `HIGH`, `VERIFIED — RUNTIME`: a single shared `localStorage` auth token with zero cross-tab coordination silently swaps a tab's identity.** An unexpected second browser tab (logged in as `manager`/OPERATIONS) appeared alongside Track C's own freshly-authenticated `admin` tab in the same Chrome profile. With both open, Track C's `admin` tab — UI still correctly showing "System Admin" — started receiving `403 Forbidden` on `GET /users?limit=500`. Decoding the actual JWT sitting in `localStorage.fapoms_token` at that moment showed it belonged to `manager`, not `admin`. Root-caused via code, not guessed: `packages/frontend/src/services/api.ts` reads the bearer token fresh from `localStorage` on every single request, but each tab's own React state (`currentUser`, the "System Admin" label) is captured once at login and never re-synced — no `storage` event listener, no `BroadcastChannel`, no tab-scoping anywhere in `packages/frontend/src`. Whichever tab most recently logged in (or silently refreshed its token on a 401) wins globally; every *other* open tab keeps displaying its own identity while silently sending that other tab's bearer token on every subsequent request. What was actually observed was the safe direction (a permission check correctly refused the swapped-in lower-privilege token) — but the reverse is exactly as easy to construct and clearly worse: a lower-privileged tab silently starts acting with a higher-privileged user's identity the moment that user logs in nearby, and every write in between would misattribute `createdBy`/`updatedBy` to the wrong person. **Fixed since** (see Report status below): `App.tsx` now listens for the `storage` event on `fapoms_token` and shows a persistent "signed in as someone else — reload?" warning rather than silently swapping identity underneath the tab. **Practical note for anyone else testing this app**: still avoid holding two tabs open under different identities where possible — the fix surfaces the collision clearly, but doesn't prevent it from happening.

**Finding — `MEDIUM`, `VERIFIED — RUNTIME`: role display names are not unique, and the field that's supposed to prevent collisions doesn't track what you type.** Created a second role literally named "HR" (the existing role is `HR_OPERATOR`, displayed as "HR") — it saved successfully as a distinct row. `roles.name` (the internal system reference) has a real DB unique constraint; `roles.display_name` (what every picker, dropdown and table in the app actually shows) does not. Compounded by a second bug: the "System Reference" field that's meant to auto-derive from the "Name" field as you type didn't stay in sync (typing "HR" left it at "H"), so the two same-named roles got different auto-derived `name` values and never collided against the one constraint that exists. Reproduced twice; both duplicate rows were cleaned up and verified gone from the DB. **Fixed since** (see Report status below): a case-insensitive uniqueness check in `UserService.createRole`/`updateRole`, backed by a DB-level unique index, plus the frontend reference-field sync corrected.

**Finding — `MEDIUM`, `VERIFIED — RUNTIME`, root cause corrected on closer read: `useScope must be used within a ScopeProvider` fires from `<Header>`, but not for the reason first suspected.** Navigating directly to `/users?tab=roles` during heavy backend-restart churn threw this error from inside `<Header>`, caught by the app's top-level `ErrorBoundary`. Track C's live observation (correlated with a `GET /scope/options → 500` moments earlier) is accurate, but reading `ScopeContext.tsx` closely afterward shows `ScopeProvider` is **not** the bug it looks like: it always renders `<ScopeContext.Provider value={value}>`, and `options` falls back to a real, safe `EMPTY_OPTIONS` object via `useMemo` whenever the `/scope/options` query has no data yet — win or lose, a failed fetch degrades to an empty-but-valid context value, never an absent one. The far more likely mechanism, given the crash's exact trigger (a Vite Fast-Refresh hot-update to an unrelated file, `/src/pages/Dashboard.tsx`, immediately preceded every occurrence reproduced during this same round of testing) is a known Vite/React Fast-Refresh limitation: a hot-reloaded module can re-run `createContext()` and mint a *new* Context object, while a still-mounted `<ScopeContext.Provider>` up the tree keeps providing the *old* one — so a freshly-hot-reloaded consumer's `useContext` reads a provider that, from its perspective, was never mounted. This is consistent with everything observed: it self-recovers on "Try again" (a fresh render tree picks up one consistent Context object again), and a genuinely idle production build — no Vite, no Fast Refresh — would not have a mechanism to trigger it at all. Downgraded from "real production resilience gap" to **likely a dev-only artifact of this session's unusually heavy, concurrent hot-reload churn**; not the "backend-error-handling gap" it first looked like. **Fixed since** (see Report status below): `useScope` now returns an inert, unscoped fallback instead of throwing when no provider is found, removing the failure mode regardless of what triggers it.

**Working correctly, confirmed by adversarial probing**:

- Invalid Platform Settings values (empty rule name, negative capacity) → correctly rejected client-side (though silently — the Save button just no-ops with no visible inline error, a minor UX gap, not a correctness bug).
- Once the stray tab was closed and a fresh `admin` session established, User Management and Roles & Permissions worked correctly end to end (63/63 permissions visible and functional).
